These file names contain hashes which randomly change when the content of the file changes, so browsers don't serve a stale cached copy,so browsers can cache old files forever and still get new ones. If they did not contain these, users would see stale Javascripts.

What do tsc -b and vite build each do? Which one produces files in dist/? tsc -b is the typescript compiler in build mode, it only type-checks the Typescript and produces no JS in dist/ . Vite build takes index.html and the code in src/ and bundles them into a few optimized files. It minifies the code (strips whitespace and shortens names) and gives files hashed names such as index-D8WT6gtn.js and produces output into dist/.

Why --frozen-lockfile? Delete pnpm-lock.yaml, reinstall, and describe what changed and why that is dangerous in CI.--frozen-lockfile installs the exact versions(of very dependency and sub-dependency) in npm-lock.yaml. Deleted it using rm pnpm-lock.yaml. Reinstalled it using pnpm install and and checked what changed using git diff --stat. pnpm install couldn't npm-lock.yaml, so it resolved every dependency again from package.json and wrote a new pnpm-lock.yaml. It is dangerous for CI because versions may drift, so a CI build may not match what you tested.


Open vite.config.ts. What do manualChunks and chunkSizeWarningLimit do? Which chunk is the largest, and why does that matter to a user on a 3G connection? manualChunks splits the bundle so big libraries (PDF, airports data, React) cache separately. chunkSizeWarningLimit silences the size warning. The PDF library is the largest chunk, and matters to a user on a 3G connection because it is heavy on 3G as user on 3G is often on a limited data plan, so heavy downloads cost them money, increases latency. This was derived with the command : ls -lS dist/assets.

Why must pnpm dev never be used to serve production traffic? Give three reasons. pnpm dev runs vite --host 0.0.0.0 which starts Vite's development server meant for developer editing code on their own machine, not for production. It is unminified(slow and heavy), no compression or caching headers(unlike a production server which compresses responses;gzip or brotli and tells browsers to cache the hashed asset files for a long time), hot reload and file watchers(the dev server watches your files and keeps a WebSocket open to every browser so it can refresh the page when you save. That costs memory and CPU for each visitor, and it has no purpose in production, because nothing is changing.), exposes source, single process with no hardening.
